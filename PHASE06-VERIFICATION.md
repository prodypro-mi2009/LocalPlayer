## SOS fixes
1. **Black rectangle behind Songs.** Root cause: `SwipeToQueueEnd` wrapped each row in `Box(background(colorScheme.background))` (opaque; black in dark theme) so the gaps around the rounded track pills painted over the custom background. Fix: content layer is transparent; the swipe hint is drawn only while dragging (`dismissDirection == EndToStart`) and is clipped to the pill. Rows themselves stay opaque pills (readable, current track highlighted). Status: implemented + static; needs on-device look.
2. **Swipe-left-to-queue everywhere.** Root cause: the gesture was wrapped around `TrackRow` only in `SongsTab`. Now `TrackRow` itself wraps in `SwipeToQueueEnd` when `SongActions.onSwipeToQueue` is set, and `SongMenuController.actionsFor()` always sets it → Songs, Album, Artist, Genre, Playlist, Favorites/Home, Search, Recently played (all use `TrackRow`). One implementation, one threshold (40%). Not covered: the Songs *grid* view cards (no swipe in a 2-column grid). Tap and menu unchanged; the gesture only appends, never plays. Needs device test, especially vs. horizontal scroll containers.
3. **Undo jumping back ~2 s.** Root cause: Undo called `restoreQueue(snapshot)` = `setMediaItems(all, index, positionAtSwipeTime)` + `prepare()` — rebuilds the whole timeline and seeks to the old position. Fix: the swipe appends ONE new occurrence tagged with a unique id (`appendOccurrence`, plain `addMediaItem`; if the queue was empty it only `prepare()`s, never plays); Undo calls `removeOccurrence(id)` = `removeMediaItem(index)` only (no setMediaItems/prepare/seek/stop). The decision rule (`QueueOccurrence.planUndo`) removes the exact occurrence (duplicates safe), is a no-op if already gone, and refuses to remove an entry that has meanwhile become the playing one. Old "move existing entry to end" behaviour was dropped (it made Undo ambiguous). JVM-tested: occurrence selection, duplicates, current-index shift, no-op cases. **Gapless playback is NOT proven** — Media3's `removeMediaItem` of a non-current item is designed not to interrupt, but this needs real-device confirmation.
4. **History control.** Replaced the `AssistChip` (icon + "Recently" text) with an icon-only `FilledTonalIconButton` (48dp, circle, 28dp history icon), pushed to the end of the Favorites control row, content description `recently_played_cd` (EN "Recently played" / EL "Πρόσφατα αναπαραγμένα"). Navigation to `Screen.Recent` unchanged.

## Configuration
- **Tab order** (`ui/components/TabOrder.kt`, `AppSettings.tabOrder`, SharedPreferences key `tabOrder`, no DB change): Settings → "Library tab order" with move up/down per tab (accessible, 48dp) and "Restore default order". `LibraryBottomNav` renders the saved order immediately; Search stays fixed at left; Years not exposed. Parse repairs null/garbage/duplicates/unknown/missing names. Drag-and-drop NOT implemented (up/down buttons instead). The initial tab at launch is the first tab of the order; the selected tab stays selected when reordered.

Stored in SharedPreferences; `MainActivity` and `PlaybackService` wrap their base context with the saved locale; changing it calls `recreate()`. No appcompat dependency; minSdk 26 safe. First launch with no saved choice follows the system language if it is Greek, otherwise English. All new strings exist in EN and EL; no hardcoded UI string literals found by grep. ViewModel-level "Unknown artist/album" now use `container.localizedContext()`. Metadata is never translated. Limitation: Android's system per-app language setting is not integrated.

## Audits
- **Lyrics.** Found two real bugs and fixed them: (a) after a save the editor ViewModel kept the pre-save snapshot (and the VM is activity-scoped), so reopening showed the OLD lyrics and a later save could resurrect deleted lines → `reloadFromFile()` after every successful save; (b) ID3 can hold several USLT frames and `setField` may add rather than replace, so `getFirst` could keep returning old lyrics → `FileTagEngine` now deletes the lyrics field before setting it. Also: deleting every line now clears the field even if LRC header tags remain; a new "Edit as text" mode lets the user paste/edit all lyrics at once (malformed `[..]` lines are kept verbatim as plain text, never rewritten; order is never re-sorted). Backup→verify→write-back→reread pipeline unchanged. JVM-tested: model/serialization semantics. NOT run: the real-file MP3/FLAC/M4A test. Not audited in depth: LyricsScreen sync UI and blurred-artwork lyrics background (only existing tests LrcParser/LyricsSync run).
- **Sleep timer.** Static review: presets 5/10/15/20/30/45/60, end-of-song (`pauseAtEndOfMediaItems`), custom minutes (1–9999), single scheduled callback (no polling), 3 s fade, cancel restores volume, ends by pause→stop→clear→`stopSelf()` and closing the app, detached with the service. No defect found; not testable on JVM (Handler/ExoPlayer). Not persisted across process death (by design).
- **Queue controls.** Move/remove/clear-upcoming use `moveMediaItem`/`removeMediaItem(s)` (no restart); shuffle/repeat are read from the player on every event. Fixed: queue list items were keyed by position; now keyed by track id + occurrence number so duplicates and reorders keep correct row identity. Undo for single removal/clear-upcoming re-inserts only (no rebuild).
- **Output-device control.** There is NO output-device UI or code in the project and it is not in the delivered spec text I have; I added none (no decorative button). The system media notification/quick-settings controls expose the Android output switcher because a MediaSession is used — unverified.
- **Mini-player swipe.** Separate code in `AppRoot` (dismiss = stop + clear queue + Undo snackbar). Undo there necessarily rebuilds the queue (it was cleared and playback stopped) using `restore(snapshot)` (items + index + position + play state); the continuity guarantee of SOS 3 applies to adds, not to this stop-and-clear action. Not touched, not device-tested.
